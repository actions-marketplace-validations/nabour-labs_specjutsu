Using specjutsu

Everything you need to go from an openspec/ folder to pull requests that can't merge unless every scenario is tested and every test was red first.

What works today

specjutsu is pre-alpha and built in the open. This manual marks every feature with its state, so you know what you can rely on.

In practice today: write and archive changes with OpenSpec, and use sj to prove them. When the authoring commands land, OpenSpec drops out and nothing in your openspec/ folder changes.

Core concepts

Specs live where OpenSpec puts them

specjutsu reads the OpenSpec layout in place. Current truth lives in openspec/specs/; in-flight changes live in openspec/changes/<change>/specs/; the archive is skipped. Use --spec-root if your folder has another name.

openspec/
  specs/auth/spec.md                 # current truth
  changes/add-token-expiry/
    proposal.md                      # why, scope, exemptions
    specs/auth/spec.md               # ADDED / MODIFIED / REMOVED
    tasks.md
  changes/archive/                   # ignored

Every scenario gets a stable ID

Put an ID of the form PREFIX-NNN at the start of each scenario name. Use one prefix per capability and never reuse an ID. Matching ignores case and treats - and _ the same, so AUTH-003 matches auth_003.

### Requirement: Expired tokens are rejected
The system SHALL reject tokens older than 24 hours.

#### Scenario: AUTH-003 Reject expired token
- **WHEN** the client calls GET /me with a token issued 25 hours ago
- **THEN** the response is 401 with code TOKEN_EXPIRED

A scenario heading with no ID isn't dropped: sj trace reports it as without ID so you can fix it.

Tests point at scenarios

Link a test by putting the ID in its name, or in a // spec: comment on the line above. No library needed.

// tests/auth.rs
#[test]
fn auth_003_rejects_expired_token() { … }

// spec: AUTH-003
#[test]
fn rejects_token_issued_yesterday() { … }

Trace states

StateMeaning
mappedThe scenario has at least one test.
gapThe scenario has no test.
orphanA test names an ID that no spec contains any more.
without IDA scenario heading has no ID.

Red-on-base

The gate's core check. It checks out the base commit, overlays only the change's test files, and runs the new tests there. They must fail. Then they must pass on the PR head. A test that already passes on the old code didn't drive the change.

  • An assertion failure on base counts as red (red:assert).
  • A compile failure on base also counts, recorded separately (red:compile). New tests often call code that doesn't exist yet.
  • Only separate test files can be overlaid. Keep scenario tests in tests/. Tests inline in source files (#[cfg(test)] mod tests) are reported as unverifiable.

The evidence ledger v0.3

sj test appends one line per test to .specjutsu/ledger/runs.jsonl: run ID, time, git tree hash, test, scenario IDs and result. It's gitignored and local. A scenario is proven when a failing run was recorded before a passing one, on different code. CI never trusts the ledger; it recomputes red and green itself.

Your first proven change

The full loop, using OpenSpec for authoring and sj for proof. The same steps work whether you type them or your agent does.

  1. Propose the change

    Create the change folder as usual: /opsx:propose add-token-expiry in your agent, or openspec new change add-token-expiry.

  2. Give every scenario an ID

    Add IDs to the delta spec's scenario headings: #### Scenario: AUTH-003 Reject expired token. Then check what's missing:

    $ sj trace
trace: 12 mapped, 1 gaps, 0 orphans, 0 without ID
gap     AUTH-003 Reject expired token  (openspec/changes/add-token-expiry/specs/auth/spec.md:9)

  3. Write the failing test first, and commit it

    Add auth_003_rejects_expired_token to tests/auth.rs. Run it and watch it fail. Commit it on its own:

    cargo test auth_003          # or, from v0.3: sj test AUTH-003
git commit -m "test(AUTH-003): red"

  4. Make it pass

    Write the implementation until the test is green, then commit:

    git commit -m "feat(AUTH-003): green"
sj trace                     # no gaps for this change

    The test(ID): red / feat(ID): green commit pair lets sj gate --since check red-before-green from history later.

  5. Open the PR

    CI runs sj gate (see Gate every PR). To preview it locally:

    $ sj gate --base origin/main
gate: pass — 1 scenario proven (1 red:compile)

  6. Archive

    After merging, fold the delta into current specs with /opsx:archive. From the planned release, that's sj spec archive.

Set up your agent

specjutsu never calls an LLM. Your agent runs sj like any other command and gets a few lines back. Until the Claude Code adapter ships, paste these rules into CLAUDE.md or AGENTS.md:

## specjutsu

- Every spec scenario starts with a stable ID: `#### Scenario: AUTH-003 …`.
  Use the capability's prefix and the next free number. Never reuse an ID.
- For each scenario, write the test first, in `tests/`, named after the ID
  (`auth_003_…`) or with `// spec: AUTH-003` on the line above.
- Run the new test and confirm it fails before touching implementation code.
  Commit it as `test(AUTH-003): red`, then implement and commit
  `feat(AUTH-003): green`.
- Before saying a task is done, run `sj trace`. It must show no gaps for the
  change you are working on.
- Never weaken or delete a test to make it pass. If a test is wrong, say so.
- For a refactor with no behaviour change, add to the change's proposal.md:
  `Exempt: refactor — <reason>`.

Why the CI gate still matters: rules in a prompt are requests. If an agent skips them, sj gate refuses the merge anyway. When the adapter ships, a pre-edit hook will also block source edits until a failing test exists.

Gate every pull request

Add a job that installs a pinned sj and runs the gate against the PR's base. It needs the full history (fetch-depth: 0) to check out the base commit, and a Rust toolchain to build and run your tests on both sides.

# .github/workflows/ci.yml
jobs:
  gate:
    if: github.event_name == 'pull_request'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - uses: dtolnay/rust-toolchain@stable
      - name: Install sj
        env:
          GH_TOKEN: ${{ github.token }}
        run: |
          gh release download v0.2.0 -R nabour-labs/specjutsu \
            -p 'sj-x86_64-unknown-linux-gnu.tar.gz' -D "$RUNNER_TEMP"
          tar -xzf "$RUNNER_TEMP/sj-x86_64-unknown-linux-gnu.tar.gz" -C "$RUNNER_TEMP"
          echo "$RUNNER_TEMP/sj-x86_64-unknown-linux-gnu" >> "$GITHUB_PATH"
      - run: sj gate --base origin/${{ github.base_ref }}

Not ready to block merges? Start with a report: sj trace | tee -a "$GITHUB_STEP_SUMMARY" prints coverage on every run without failing it. Add --strict when you want gaps to fail.

What fails the gate

ReasonWhat happened
untested AUTH-004An added, modified or newly implemented scenario has no test.
failing AUTH-004 <test>A mapped test fails on the PR head.
not-run AUTH-004 <test>A mapped test didn't run.
green-on-base AUTH-004 <test>The new test already passes on the old code.
unverifiableThe test is inline in a source file and can't be overlaid. Move it to tests/, or pass --allow-unverifiable to warn instead.
orphan AUTH-003 <test>A test points at a scenario that was removed.
unspecified changeSource files changed with no added or modified scenario and no exemption.
exemption needs a reasonAn exemption line has no reason.
spike cannot merge to mainA spike exemption targets main.

Changes that touch only docs, specs, CI or other non-source files pass without an exemption. Unchanged scenarios without tests show up as warnings, not failures, so you can adopt specjutsu in an existing repo and tighten coverage as you go.

Exemptions

Some changes don't add behaviour. Declare them explicitly, with a reason. Every exemption appears in the gate summary.

# in the change's proposal.md
Exempt: refactor — extract token parser

# or, for changes without a change folder, as a commit trailer
Specjutsu-Exempt: chore — bump dependencies
KindEffect
refactorSkips red-on-base and the unspecified-change rule; the full test suite must still pass.
docs, config, choreNo scenario required.
spikeAllowed on spike/* branches; blocked from merging to main.

Command reference

Every command takes --json for tools and agents. Exit codes are shared: 0 pass, 1 fail, 2 usage or environment error.

sj trace v0.2.0

Map spec scenario IDs to tests; list gaps and orphans.

--json
JSON instead of the compact report.
--strict
Exit 1 when there are gaps or orphans.
--spec-root <dir>
Spec folder, relative to the repo root. Default openspec.
--root <dir>
Repository root. Default: the current directory.

sj gate v0.2.0

CI check: every changed scenario tested, red on base, green on head.

--base <ref>
Base to compare against, e.g. origin/main. A ref that doesn't resolve exits 2 with a hint about fetch-depth: 0.
--since <commit>
Check commit history instead: every feat(ID) commit needs an earlier test(ID): red. IDs can be ranges (TRACE-001..006) or comma-separated.
--allow-unverifiable
Warn instead of failing when a test can't be overlaid on base.
--json, --root, --spec-root
As for trace.

sj test [scope] v0.3

Run the tests and print failures only. A green run is one summary line; each failure shows its scenario IDs and the first 20 lines of output. A compile error is reported as build failed, never as an empty run. Records the run in the ledger.

scope
A scenario ID (AUTH-003) runs just its tests; a Cargo package name runs that package. Omit to run everything.
--no-ledger
Don't record this run.
--json, --root, --spec-root
As above.

sj ledger [ID] v0.3

Per scenario: the latest result, and whether red-before-green is proven.

ID
Report only this scenario.
--json, --root
As above.

Coming from OpenSpec

specjutsu keeps OpenSpec's format and replaces its workflow. Today you keep the /opsx:* commands and add sj for proof. As the planned releases land, each command gets a specjutsu equivalent, driven by a skill that calls the binary instead of reading whole folders.

OpenSpecTodayspecjutsu (planned)
/opsx:exploreKeep using itsj-explore skill
/opsx:propose, /opsx:updateKeep using it; add scenario IDssj-propose → sj spec new, sj spec validate
nonenonesj-clarify → sj spec check: uncovered scenarios, open questions
/opsx:applyKeep using it, test first, then sj tracesj-apply → sj next, sj test <ID>, sj task done
nonesj gate locallysj-verify → sj verify
/opsx:archive, /opsx:syncKeep using itsj-finish → sj spec archive

What changes for you

  • Your agent stops reading folders. sj status answers "where am I" in ten lines; sj next returns only the current task, its scenarios and the exact test command.
  • "Done" is checked, not claimed. In strict mode sj task done refuses to tick a task until the ledger shows its tests went red, then green.
  • TDD is enforced, not requested. With the adapter, editing source before a failing test exists is blocked. Writing the test is always allowed.
  • Your specs don't move. Same folders, same headings. The switch is a config change, not a migration.

FAQ

Does specjutsu call an AI model?

No. It's a deterministic binary. Your agent calls it; it never calls your agent or any LLM.

Which languages work today?

Rust with cargo test. pytest, Jest/Vitest, Playwright, Go, JUnit, dotnet, PHPUnit and RSpec are on the roadmap, mostly through JUnit XML reports.

Can I adopt it in an existing repo?

Yes. Only scenarios a change adds or modifies must be tested; existing untested scenarios are warnings. Add IDs as you touch specs, and add sj trace to CI as a non-blocking report first.

Why must tests live in tests/?

Red-on-base overlays the change's test files onto the base commit. A test inside a source file can't be moved without also moving the new code, so it's reported as unverifiable.

Is the local ledger trusted by CI?

No. A local file is easy to forge, so CI recomputes red and green itself with red-on-base. The ledger is local evidence for your workflow and for strict mode.

Can I check red-before-green on work I've already done?

If you used test(ID): red and feat(ID): green commit subjects, yes: sj gate --since <first-commit> checks the history.
