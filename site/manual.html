User manual · v0.4.0

Using specjutsu

Everything you need to go from an openspec/ folder, a Spec Kit project or a Superpowers setup to pull requests that can't merge unless every scenario is tested and every test was red first.

What works today

specjutsu is pre-alpha and built in the open; the beta opens with v0.5. This manual marks every feature with its state, so you know what you can rely on.

In practice today: specjutsu runs the whole loop on its own, from sj spec new to sj spec archive. You don't need OpenSpec, Spec Kit or Superpowers alongside it, and sj migrate removes them for you.

Install

One binary, no runtime. The installers download the latest release for your platform, check it against the release's SHA256SUMS and install sj.

# macOS and Linux: installs into ~/.local/bin and prints the PATH line if it's missing
curl -fsSL https://nabour-labs.github.io/specjutsu/install.sh | sh

# Windows: installs into %LOCALAPPDATA%\Programs\sj and adds it to your user PATH
powershell -ExecutionPolicy ByPass -c "irm https://nabour-labs.github.io/specjutsu/install.ps1 | iex"

# Homebrew (macOS and Linux)
brew install nabour-labs/tap/specjutsu

# Cargo: binstall downloads the release binary, install builds from source
cargo binstall specjutsu
cargo install specjutsu

sj --version

Both installers read SJ_VERSION (a release such as 0.4.0, default the latest) and SJ_INSTALL_DIR. install.ps1 also reads SJ_NO_MODIFY_PATH=1, which leaves your PATH alone. install.sh never edits shell profiles. To update, run the installer again or brew upgrade specjutsu.

The archives are on the releases page:

Shell completions

sj completions <shell> prints a completion script for bash, zsh, fish, powershell or elvish, built from the binary's own commands and flags. It writes no file: save the output where your shell looks, and regenerate it after upgrading.

# bash
sj completions bash > ~/.local/share/bash-completion/completions/sj
# zsh: then add fpath=(~/.zfunc $fpath) before compinit in ~/.zshrc
mkdir -p ~/.zfunc && sj completions zsh > ~/.zfunc/_sj
# fish
sj completions fish > ~/.config/fish/completions/sj.fish
# elvish: then add `use sj` to ~/.config/elvish/rc.elv
sj completions elvish > ~/.config/elvish/lib/sj.elv
# PowerShell: add this line to $PROFILE
sj completions powershell | Out-String | Invoke-Expression

Update or reinstall

Install over the old binary: --force replaces the sj already in ~/.cargo/bin. With a prebuilt archive, download the new release as above and run install again.

# the latest release, from crates.io
cargo install specjutsu --force

# a fix that is merged but not released yet, from main on GitHub
cargo install --git https://github.com/nabour-labs/specjutsu --branch main specjutsu --force

# which build is installed, and where it came from
cargo install --list | grep -A1 specjutsu

sj --version names the build. One made from a git checkout, including cargo install --git, prints the short commit after the version, such as sj 0.4.0 (f62a48b). One from crates.io or a release archive prints only the version. cargo install --list also names the source: a build from GitHub shows the repository URL and commit in brackets after the version.

Agent hooks call sj from PATH, so sessions that are already open use the new binary on their next edit, with no restart. Then run sj update in each project, so the generated skills, hooks and agent instructions match the new version. Files you edited by hand are kept and reported.

Set up a project

Pick the line that matches where you're starting from. Each one writes specjutsu.toml, which says where the specs are and which packages and test suites the project has.

# a new project
sj init --agents claude

# an existing project without a spec tool
sj adopt --dry-run        # print the detected packages and runners
sj adopt
sj init --agents claude

# a project on OpenSpec, Spec Kit or Superpowers
sj migrate --from openspec --from superpowers           # dry run
sj migrate --from openspec --from superpowers --write   # needs a clean git tree

# then check it
sj doctor

sj adopt reads Cargo, pnpm, npm and yarn workspaces and pyproject.toml, and detects cargo, vitest, jest, pytest and playwright without running anything. sj doctor lists config errors, packages without a runner, runners that aren't installed and missing spec folders.

# specjutsu.toml, as sj adopt writes it for a pnpm app with a uv worker
schema = 1
spec_root = "specjutsu"
mode = "guided"

[[package]]
path = "apps/app"
sources = ["apps/app/**"]

[[package.suite]]
runner = "vitest"
tests = ["apps/app/**/*.{test,spec}.{ts,tsx,js,jsx,mts,cts}"]
setup = "pnpm install --frozen-lockfile"

[[package]]
path = "python/worker"
sources = ["python/worker/**"]

[[package.suite]]
runner = "pytest"
tests = ["python/worker/**/test_*.py", "python/worker/**/*_test.py"]

mode sets how strict the agent loop is: strict refuses to tick a task until its scenarios are proven, guided warns, advisory only reports. The CI gate is the same in every mode.

Core concepts

Where specs live

Current truth lives in specjutsu/specs/; in-flight changes live in specjutsu/changes/<change>/; the archive is read for IDs and never written. Set spec_root in specjutsu.toml (or pass --spec-root) if your folder has another name. A project with only an openspec/ folder keeps using it.

specjutsu/
  principles.md                      # project rules the agent reads
  specs/auth/spec.md                 # current truth
  changes/add-token-expiry/
    proposal.md                      # why, scope, exemptions
    design.md
    specs/auth/spec.md               # ADDED / MODIFIED / REMOVED / RENAMED
    tasks.md                         # each task names its scenario IDs
  changes/archive/

Every scenario gets a stable ID

Each scenario name starts with an ID of the form PREFIX-NNN, one prefix per capability, never reused. Matching ignores case and treats - and _ the same, so AUTH-003 matches auth_003.

### Requirement: Expired tokens are rejected
The system SHALL reject tokens older than 24 hours.

#### Scenario: AUTH-003 Reject expired token
- **WHEN** the client calls GET /me with a token issued 25 hours ago
- **THEN** the response is 401 with code TOKEN_EXPIRED

Existing specs don't need editing by hand. sj ids --write adds IDs to every scenario without one, changing only the headings. Prefixes come from the capability folder (user-auth → USERAUTH) unless you map them under [ids.prefixes], and a delta copy in an open change gets the same ID as its spec.

Tests point at scenarios

Link a test by putting the ID in its name or title, or in a spec: comment on the line above. No library needed.

// vitest, Jest, Playwright: the title, a describe title, or a comment
it("AUTH-003 rejects expired token", () => { … })

describe("AUTH-004 refresh", () => {
  it("issues a new token", () => { … })   // covered by AUTH-004
})

# pytest: the function name, a marker, or a comment
def test_auth_003_rejects_expired(): …

@pytest.mark.spec("AUTH-005")
def test_rotates_key(): …

// Rust: the function name or a comment
// spec: AUTH-006
#[test]
fn rejects_token_issued_yesterday() { … }

Titles built at runtime (variables, ${} templates) aren't read; use a spec: comment for those.

Red-on-base

The gate's core check. It checks out the base commit, overlays only the change's test files, and runs the new tests there. They must fail. Then they must pass on the PR head. A test that already passes on the old code didn't drive the change.

  • It runs per suite. Every changed file matching a suite's tests or support globs is overlaid, so a co-located auth.test.ts runs against the base auth.ts.
  • An assertion failure on base counts as red (red:assert). A test that fails to compile or load, because it calls code that doesn't exist yet, counts too (red:compile).
  • A base checkout has no installed dependencies, so a suite can declare setup (e.g. pnpm install --frozen-lockfile), run once before its base run.
  • A suite that can't run on old code, such as end-to-end tests against a deployed API, sets red_on_base = "skip" with a reason. Its new tests are unverifiable, and its head run still happens.
  • Rust tests inline in source files (#[cfg(test)] mod tests) can't be overlaid and are reported as unverifiable. Keep scenario tests in tests/.

The evidence ledger

sj test appends one line per test to .specjutsu/ledger/runs.jsonl: run ID, time, git tree hash, test, scenario IDs and result. It's gitignored and local. A scenario is proven when a failing run was recorded before a passing one, on different code. The agent loop and the pre-edit hook read it; CI never trusts it and recomputes red and green itself.

Your first proven change

The full loop with sj alone. The same steps work whether you type them or your agent does; with the Claude Code adapter, the sj-propose, sj-apply and sj-finish skills run them for you.

  1. Create the change

    $ sj spec new add-token-expiry
created specjutsu/changes/add-token-expiry
next AUTH-003

    Write proposal.md, the delta spec under specs/, design.md and tasks.md. Each task names the scenarios it covers: - [ ] 1.1 Reject expired tokens (AUTH-003).

  2. Check the plan

    sj spec validate add-token-expiry   # format, IDs, deltas, task links
sj spec check add-token-expiry      # uncovered scenarios, open questions

  3. Write the failing test first, and commit it

    sj next prints the task, its scenario text and the test command. Add the test, watch it fail, and commit it on its own:

    $ sj test AUTH-003
test: fail — 1 failed, 0 passed
fail    src/auth.test.ts › AUTH-003 rejects expired token  AUTH-003
git commit -m "test(AUTH-003): red"

  4. Make it pass

    Implement until the test is green, tick the task and commit:

    sj test AUTH-003
sj task done add-token-expiry 1.1   # strict mode needs red-before-green
git commit -m "feat(AUTH-003): green"

    The test(ID): red / feat(ID): green commit pair lets sj gate --since check red-before-green from history later.

  5. Verify and open the PR

    $ sj verify
verify: ok
$ sj gate --base origin/main        # what CI will run
gate: pass — 1 scenario proven (1 red:assert)

  6. Archive

    After merging, fold the delta into current specs:

    sj spec archive add-token-expiry   # → changes/archive/YYYY-MM-DD-add-token-expiry/
sj spec archive --all-done         # every change whose tasks are all done, as one operation

Set up your agent

specjutsu never calls an LLM. Your agent runs sj like any other command and gets a few lines back.

sj init --agents claude          # install
sj update                        # regenerate; hand-edited files are kept
sj update --dry-run              # preview each write, keep and remove; change nothing
sj init --remove-agents claude   # remove everything it added

The Claude Code adapter writes three things and touches nothing else:

  • A block in CLAUDE.md between <!-- specjutsu:begin --> and <!-- specjutsu:end -->, under 1,200 bytes.
  • Ten skills under .claude/skills/sj-*/: explore, propose, clarify, principles, apply, debug, review, verify, finish and onboard. New to specjutsu? Ask your agent to onboard you: sj-onboard runs one toy change through the whole loop in a scratch change, sj-onboard-demo, then deletes it without archiving, so your specs are unchanged. It won't start on a dirty working tree.
  • Two hooks in .claude/settings.json, added after yours. The file is edited as text, so your formatting, permissions and other hooks stay byte for byte.
HookWhat it does
sj hook claude session-startPrints the sj status lines and the active task, in at most 1,200 bytes.
sj hook claude pre-editBefore Edit, Write, MultiEdit and NotebookEdit on a source file, blocks the edit until each scenario of the active task has a red run in the ledger. Tests, specs and docs are always allowed. advisory mode only warns.

Codex, Cursor, Cline, Copilot, Gemini CLI, Windsurf, Kiro, Antigravity and AGENTS.md

sj init --agents codex,cursor    # several at once; AGENTS.md is written once
sj init --agents auto            # the agents the repo already has files for
sj init --agents claude,codex --global  # the skills only, in your home folder
sj doctor                        # hook, instructions or hook missing, per agent

Hook entries are added after yours and removed byte for byte. A hook that can't read its input allows the edit with a warning. For any other agent or editor with hooks, sj hook check-edit <path> exits 0 to allow and 2 to block, with the reason on stderr.

Skills. Codex, Gemini CLI and Antigravity load skills from .agents/skills/, so installing any of them writes the ten sj-* skills there beside .claude/skills/. sj update keeps both copies in step; removing the last of the three removes the sj-* skills and keeps yours. --global on sj init, sj update and --remove-agents acts on ~/.claude/skills/ and ~/.agents/skills/ instead and writes nothing in the repository. sj doctor prints skills: project, global or project, global.

Whatever the agent does, sj gate in CI refuses unproven work. Hooks stop it earlier; the gate is the backstop.

Gate every pull request

Add the specjutsu action, published on the GitHub Marketplace as specjutsu gate. It installs a pinned sj (verified against the release's checksums), runs the gate against the PR's base, writes the job summary and keeps one PR comment up to date. It needs the full history (fetch-depth: 0) to check out the base commit, and the toolchains your suites use (Rust, Node, uv) to run tests on both sides.

# .github/workflows/specjutsu.yml
on: pull_request
jobs:
  gate:
    runs-on: ubuntu-latest
    permissions: { contents: read, pull-requests: write }
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      # set up your toolchains and install dependencies here
      - uses: nabour-labs/specjutsu@v0

Inputs: fail-on: never reports without failing the step, comment: false writes only the job summary, and badge: true (on pushes to the default branch, with contents: write) publishes a spec coverage badge to the sj-badge branch. Other CI systems can run sj gate --base origin/main directly, or --format markdown for the comment body.

Not ready to gate? Start with a report: sj trace | tee -a "$GITHUB_STEP_SUMMARY" prints coverage on every run without failing it. Add --strict when you want gaps to fail.

What fails the gate

ReasonWhat happened
untested AUTH-004An added, modified or newly implemented scenario has no test.
unidentified <file>:<line>A new or edited scenario has no ID.
failing AUTH-004 <test>A mapped test fails on the PR head.
not-run AUTH-004 <test>A mapped test didn't run.
green-on-base AUTH-004 <test>The new test already passes on the old code.
unverifiable AUTH-004 <test>The test can't run on base: inline in a Rust source file, or in a suite with red_on_base = "skip". Pass --allow-unverifiable to warn instead.
orphan AUTH-003 <test>A test points at a scenario that was removed.
unspecified changeSource files changed with no added or modified scenario and no exemption.
exemption needs a reasonAn exemption line has no reason.
spike cannot merge to mainA spike exemption targets main.

The gate fails closed: any changed file is source unless it's a test, a spec, documentation or media, repository metadata (.github/, .gitignore, LICENSE) or a manifest or lockfile. When a package declares sources, only files matching them count, and a top-level non_source = ["infra/**"] adds your own globs. With no test suite configured, the gate exits 2 and suggests sj adopt instead of passing changes it can't test.

Unchanged scenarios without tests show up as warnings, not failures, so you can adopt specjutsu in an existing repo and tighten coverage as you go. A commit that only adds IDs counts as unchanged.

Exemptions

Some changes don't add behaviour. Declare them explicitly, with a reason. Every exemption appears in the gate summary.

# in the change's proposal.md
Exempt: refactor — extract token parser

# or, for changes without a change folder, as a commit trailer
Specjutsu-Exempt: chore — bump dependencies
KindEffect
refactor, docs, config, choreNo scenario required and no red-on-base. When source files change, the full test suite still runs at head and must pass.
spikeAllowed on spike/* branches; blocked from merging to main.

Command reference

Exit codes are shared: 0 pass, 1 fail, 2 usage or environment error. Most commands take --json for tools and agents, --root <dir> for the repository root, and --spec-root <dir> to override spec_root. Run sj <command> --help for the full list.

Proof

sj trace

Map spec scenario IDs to tests; list gaps and orphans. Each test in --json carries its package, suite and whether it's skipped.

--strict
Exit 1 when there are gaps or orphans.

sj gate

CI check: every changed scenario tested, red on base, green on head.

--base <ref>
Base to compare against, e.g. origin/main. A ref that doesn't resolve exits 2 with a hint about fetch-depth: 0.
--since <commit>
Check commit history instead: every feat(ID) commit needs an earlier test(ID): red.
--allow-unverifiable
Warn instead of failing when a test can't run on base.

sj test [scope]

Run every suite and print failures only. A green run is one line; each failure shows its scenario IDs and the first 20 lines of output. A compile error is build failed, never an empty run. Records the run in the ledger.

scope
A scenario ID (AUTH-003), a package (apps/api) or one suite (apps/app:playwright). Omit to run everything.
--no-ledger
Don't record this run.

sj ledger [ID]

Per scenario: the latest result, and whether red-before-green is proven.

Project setup

sj init

Write specjutsu.toml and create the spec folders.

--agents <list>
Install agent adapters: claude, codex, cursor, cline, copilot, gemini, windsurf, kiro, antigravity, agents-md, or auto for the agents the repo already has files for. --remove-agents <list> removes them.
--global
With --agents or --remove-agents: install or remove only the skills, in ~/.claude/skills and ~/.agents/skills, for every project.
--force
Replace an existing specjutsu.toml.

sj adopt

Detect an existing project's packages and runners and write specjutsu.toml. Never runs a tool.

--dry-run
Print the config instead of writing it.
--force
Replace an existing file.

sj doctor

Check the project file, packages, runner executables and spec folders, one problem per line, then one line per installed agent and a skills: line saying whether the skills are in the project, global or both. Never installs anything.

sj update

Regenerate installed agent adapters. A file you edited by hand is kept and reported, and the command exits 1.

--force
Replace hand-edited files too.
--dry-run
Print one write, keep or remove line per file and change nothing; adapters up to date when there is nothing to do. Exits 0.
--json
With --dry-run: {"files": [{"path", "action"}]}.
--global
Refresh the skills installed with sj init --global instead of the repository's.

sj completions <shell>

Print a completion script for bash, zsh, fish, powershell or elvish to stdout. Any other shell exits 2. See Install for where to save it.

sj ids

List scenarios without IDs and the IDs they would get; exits 1 when there are any.

--write
Insert them, changing only the headings.

Authoring

sj spec new <change>

Create changes/<change>/ with proposal.md, design.md, tasks.md and specs/, and print the next free ID per prefix.

sj spec list

One line per open change: tasks done, scenarios added or modified.

sj spec show <item>

Print one scenario, change or capability. Looked up as a scenario ID, then an open change, then an archived change (folder name, or bare name when only one matches), then a capability. A scenario prints with its requirement, steps, mapped tests and latest ledger result; a capability prints its spec.md unchanged. An unknown item exits 1 and suggests near names.

--json
The same data, with kind set to scenario, change or capability.

sj spec validate [change]

Scenario IDs and steps, requirement wording, delta structure, and that every task names its scenarios. Each problem has a file and line.

--strict
Fail on warnings too.

sj spec check <change>

Scenarios no task names, tasks naming unknown IDs, and [NEEDS CLARIFICATION] markers.

sj spec archive <change>…

Merge the deltas into specs/ (same bytes as openspec archive) and move the change to changes/archive/YYYY-MM-DD-<change>/. Several names archive together, in name order: if any one is refused, nothing is written and every problem is listed. Two changes that modify, remove or rename the same requirement are refused.

--all-done
Archive every open change with at least one task and all of them done; nothing to archive when there are none.
--force
Archive despite validation errors and open tasks. Conflicts between changes are refused anyway.

Agent loop

sj status [change]

At most five lines per open change: tasks done, scenarios by evidence (proven, green-unproven, red, untested), and the next task.

sj view

A one-screen dashboard in at most 40 lines: capabilities with scenario counts, open changes with tasks and evidence, evidence totals, orphan tests and archived changes. Reads files and the ledger only; never runs tests.

--json
capabilities, changes, totals, orphans and archived.

sj next [change]

The next task, the text of each scenario it names, the files changed since the merge-base, principles.md, and a sj test <ID> command per scenario.

--parallel
List open [P] tasks in batches that share no test file.
--base <ref>
Base for changed files.

sj task done <change> <task>

Tick the task's box and change no other byte. In strict mode it refuses unless every scenario the task names is proven.

sj verify [change]

The local check before a PR: the change's scenario tests, unproven scenarios, orphans, sj spec check problems, and the gate's rules against the merge-base, without red-on-base.

--base <ref>
Base to compare against.

Migration

sj import speckit

Preview converting Spec Kit's specs/NNN-*/ features to the OpenSpec layout. --write converts; it never touches specs/ or .specify/.

sj migrate --from <tool>

Replace openspec, speckit or superpowers (repeatable). A dry run unless --write, which needs a clean git tree and leaves the changes uncommitted.

Migrating from other tools

sj migrate replaces the old tool in one step, so two workflows don't compete for your agent. Every run writes specjutsu.toml if it's missing, installs the Claude Code adapter, then prints sj doctor and sj spec validate. Review with git diff; undo with git restore . && git clean -fd.

FromWhat sj migrate does
openspecKeeps openspec/ as the spec root and gives every scenario an ID. Moves config.yaml's guidance to principles.md. Removes OpenSpec's generated skills and /opsx commands; your own skills stay.
speckitImports every feature, then removes .specify/, the imported specs/NNN-*/ folders and the agent files Spec Kit's manifests list.
superpowersRemoves the plugin, its marketplace and its permission rules from .claude/settings.json, keeping every other byte. Lists files under docs/superpowers/ for you to review.

What changes for you

  • Your agent stops reading folders. sj status answers "where am I" in a few lines; sj next returns only the current task, its scenarios and the exact test command.
  • "Done" is checked, not claimed. In strict mode sj task done refuses to tick a task until the ledger shows its tests went red, then green.
  • TDD is enforced, not requested. The pre-edit hook blocks source edits before a failing test exists. Writing the test is always allowed.
  • Your specs don't move. OpenSpec folders stay where they are; Spec Kit features become the same layout.

FAQ

Does specjutsu call an AI model?

No. It's a deterministic binary. Your agent calls it; it never calls your agent or any LLM.

Which languages work today?

Rust (cargo test), TypeScript and JavaScript (vitest, Jest, Playwright) and Python (pytest), plus any runner that writes a JUnit XML report through a junit suite with your own command. Native test discovery for Go, dotnet, PHPUnit and RSpec is on the roadmap.

Can I adopt it in an existing repo?

Yes. Run sj adopt and sj ids --write, or sj migrate if you're on OpenSpec, Spec Kit or Superpowers. Only scenarios a change adds or modifies must be tested; existing untested scenarios are warnings.

Does it work in a monorepo?

Yes. Each package in specjutsu.toml has its own suites, and a file belongs to the package with the longest matching path. sj test apps/api runs one package; the gate runs red-on-base per suite.

Do my tests have to live in tests/?

Only Rust's. Red-on-base overlays every changed file that matches a suite's tests globs, so co-located *.test.ts files work. Rust tests inline in a source file can't be moved without the new code, so they're reported as unverifiable.

Is the local ledger trusted by CI?

No. A local file is easy to forge, so CI recomputes red and green itself with red-on-base. The ledger is local evidence for the agent loop, the pre-edit hook and strict mode.

Can I check red-before-green on work I've already done?

If you used test(ID): red and feat(ID): green commit subjects, yes: sj gate --since <first-commit> checks the history.
